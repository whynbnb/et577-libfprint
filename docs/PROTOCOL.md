# EH577 USB 协议笔记

以下内容来自对厂商 Windows UMDF 驱动（ETU813 3.6.2.3）的逆向，以及一次 Windows 驱动与设备通信的 USB 抓包分析。协议只涉及设备控制/图像数据，不包含任何生物特征样本。

## 设备与端点

- VID/PID：`1c7a:0577`
- Interface 0（vendor specific）
- Bulk OUT：`0x01`（512 字节包）
- Bulk IN：`0x82`（512 字节包）
- 另有 `0x83`、`0x84` 两个 interrupt IN 端点，但厂商驱动在此场景未使用。

## 命令格式

所有命令以 ASCII `EGIS` 开头，后跟命令字节和参数：

```
45 47 49 53  <cmd> <p1> <p2> ...
```

设备响应以 ASCII `SIGE` 开头：

```
53 49 47 45  <...>
```

**响应长度不固定**（实测有 7、9、10、13、18 字节），不要假设响应长度等于命令长度。建议用一个足够大的缓冲区读取，并只校验前 4 字节是否为 `SIGE`。

例如命令 `62 67 03` 的响应是 10 字节：

```
53 49 47 45 67 03 01 6c 73 6f
```

## 初始化

初始化由三段组成（完整字节序列见驱动源码中的 `et577_init1`、`et577_init2`）：

1. **init1**：一系列寄存器写（`0x60/0x61/0x63`），每条命令读一次响应。
2. **校准**：
   - 发送 `45 47 49 53 73 0f 96`
   - 紧接着发送 **3990 字节校准数据**（`et577_calib_data.h`）
   - 然后读取 7 字节响应（实测 `53 49 47 45 0f 96 01`）
3. **init2**：另一组寄存器写，最后一条是 `60 00 02`。

init2 结束后设备处于“可采集”状态：直接发送图像命令 `64 0f 96` 并读取 3990 字节即可得到第一帧。

## 图像

一次采集 = 命令 `45 47 49 53 64 0f 96` 之后的一次 bulk IN 读取，固定 **3990 字节**。

3990 = **70 × 57**（行优先）。判断依据：

- 对垂直方向做自相关，在 lag=70 处有明显峰值；
- 按 70×57 显示可得到清晰的指纹脊线图。

## 手指检测（轮询）

init2 后（或一次采集批次结束后）可以进入轮询模式：

```
发送： 45 47 49 53 60 01 06
读取： 7 字节响应
```

响应第 6 字节（索引 5）：

- `0x00`：无手指
- `0x04`：检测到手指

即：

```
53 49 47 45 01 00 01   -> 无手指
53 49 47 45 01 04 01   -> 有手指
```

轮询是设备自身的能力，不会采集图像，因此适合长时间等待手指。

## 采集批次

设备不应该被无限连续采集（固件可能挂死）。厂商驱动的做法是：

1. 轮询检测到手指；
2. 发送“启动采集”序列（20 条命令，见驱动 `et577_start_burst`）；
3. 发送 `64 0f 96` 读取一帧；
4. 后续帧之间发送“重复”序列（8 条命令，见 `et577_repeat`）；
5. 采集若干帧后，发送“停止/回到轮询”序列（9 条命令，见 `et577_stop_burst`，其中最后一条是 `71 45 06 ...`）；
6. 回到轮询。

本驱动每次只采集 3 帧，以降低固件压力。

## 其他注意事项

- 不要对设备执行 USB reset 或反复 authorized 切换，可能导致固件挂死；挂死后通常需要完全断电（或重启）恢复。
- 若一次 bulk 传输报 “device sent more data than requested”（overflow），可视为成功并忽略（读取到的前 N 字节有效）。
- 设备响应可能比你请求的长度短；同步 API 中不要因为长度不匹配就判定失败，但图像读取必须恰好得到 3990 字节。
